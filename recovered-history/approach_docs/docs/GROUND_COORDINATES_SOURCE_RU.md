# Наземный порт: подтверждённая цепочка исходного вектора

Исследование после 10.18. Здесь зафиксирована система координат исходного наземного порта. Она не доказывает соответствие современной картографической широте/долготе Земли и не восстанавливает исходные материки, высоты или часы вращения планеты.

## Цепочка вызовов

Источник — `/workspace/ffe-upstream/jjffe/ffe.asm`, локальная реализация JJFFE. Указанные строки относятся к этому файлу.

1. `FUNC_000880`, ветвь наземного объекта `type == 0x23` около строки 64767, передаёт слова записи `+0x12` и `+0x22` в `FUNC_000879`.
2. `FUNC_000879`, строка 64353, вызывает `FUNC_001674_MatBuildOdd(entity, phase, latitude_angle)`. Затем берёт три компоненты матрицы объекта по смещениям `+0x0c`, `+0x10`, `+0x14` как направление радиуса. Их умножают на размер модели родительской планеты. Дальнейшие вызовы `FUNC_000574` корректируют радиальную длину по местному рельефу; ориентация радиуса от этого не заменяется.
3. `FUNC_001674_MatBuildOdd`, строка 101462, строит матрицу из `FUNC_001914_Sin32` и `FUNC_001521`.
4. В `FUNC_000880` наземный объект получает `entity[0x56] = parent_id`, `entity[0x57] = 1`, флаг `entity[0x14c] |= 0x20`. Записанный вектор по `+0x3e`, `+0x46`, `+0x4e` находится в системе родительской планеты.
5. `FUNC_001677`, строка 101683, рекурсивно вычисляет положение родителя. Для ненулевого `entity[0x57]` преобразует вектор через матрицу родителя с помощью `FUNC_001669_VecMatMul`, восстанавливает масштаб и добавляет положение родителя. Это подтверждает привязку порта к вращающейся планете, а не отдельную орбиту.

`FUNC_000866`, строка 60570, при флаге `0x20` пропускает изменение орбитальной фазы объекта. Вызываемая в этой ветви `FUNC_000865` обновляет состояние станции (`+0xc9`, `+0x9e`), а не географическое направление.

## Точная арифметика направления

Пусть `p` — слово записи `+0x12`, `q` — слово `+0x22`, полный оборот равен 65536. Обозначим исходную целочисленную функцию синуса как `S`, произведение Q31 как `M`:

```text
M(a,b) = signed_i32((signed_i64(a) * signed_i64(b)) >> 31)
sp = S(p)
cp = S(p + 0x4000)
sq = S(q)
cq = S(q + 0x4000)
radial_q31 = [M(cq,cp), sq, -M(cq,sp)]
```

Это именно значения `matrix[+0x0c]`, `matrix[+0x10]`, `matrix[+0x14]`, которые использует F879. F1521, строка 90809, делает знаковое `imul`, сдвигает пару EDX:EAX влево на один бит и возвращает EDX; результат соответствует арифметическому сдвигу произведения вправо на 31.

F1914, строка 132905, читает четверть синусной таблицы `DATA_007975` из `ffebmp.asm` (начало около строки 42309). В ней 16384 знаковых 32-битных значения. При `i = angle & 0x3fff` и `quadrant = (angle >> 14) & 3`:

```text
quadrant 0:  table[i]
quadrant 1:  table[0x3fff - i]
quadrant 2: -table[i]
quadrant 3: -table[0x3fff - i]
```

Обычные `sin`/`cos` дают ту же аналитическую форму, но не побитовое совпадение с таблицей и округлением произведений. Независимые контрольные примеры должны исполнять исходные F1674/F1914/F1521, а не повторять только эту формулу в тесте.

## Каноническая запись в текущих осях проекта

Направление проекта `Link.direction(lat, lon)` равно `(cos(lat)*cos(lon), sin(lat), -cos(lat)*sin(lon))`. Оно совпадает с указанными исходными осями. Без предположения о диапазоне `q` из исходного вектора можно получить:

```text
latitude  = atan2(y, sqrt(x*x + z*z))
longitude = atan2(-z, x)
```

При радиусе горизонтальной проекции, равном нулю, долгота не определена; для хранения можно выбрать ноль. Нормализация вектора не меняет эти углы. Нельзя просто объявить `q*TAU/65536` канонической широтой: `q` может находиться вне диапазона ±четверть оборота, и тогда знак горизонтальной части меняет каноническую долготу.

Это широта/долгота **исходной системы осей модели планеты**. Например, исходный вектор London не следует исправлять по современной широте Лондона: ориентация рисунка Земли, исходное состояние модели и её система отсчёта пока не сопоставлены с современной геодезией.

## Что ещё отделено от этой работы

Мировая формула исходного движка: `parent_world_position + parent_matrix * parent_fixed_displacement`. Текущий проект использует собственный `Link.spin()` и адаптированную матрицу орбитальной связи. Перенос направления наземного порта не делает это вращение и наклон точными исходными эфемеридами.

Исходные поля вращения/наклона проходят через F880 и F1675, а обновляются F866. В локальном F873 после вычисления слова `record[+0x42]` оно дополнительно обнуляется. Поэтому исходный наклон нельзя восстанавливать по одному аргументу конструктора без отдельного сравнения исполняемой версии игры.

В 10.19–10.20 исходные упакованные слова, их происхождение и подтверждённое направление подключены к новым входам через отдельную ревизию **`sphere-source-sites-v2`**. Проверены 675 нативных случаев, направления 21 наземного порта, заданного вручную, и всех 16 пар процедурной таблицы. Старые `sphere-v1` продолжают читать с прежними художественными положениями, рельефом и зданиями; совместимость проверена на семи настоящих состояниях версии 0.10.7. Орбитальная связь без явной ревизии географии сохраняет прежнее значение по умолчанию. [Текущий отчёт и границы](STAGE10_19_20_RU.md).

Это подключение исходного планетного направления порта. Исходные мировое вращение и наклон, полный запрос высоты, материки и геометрия городов ещё не перенесены. Смена системы координат не перемещает площадку под старым сохранённым кораблём.
