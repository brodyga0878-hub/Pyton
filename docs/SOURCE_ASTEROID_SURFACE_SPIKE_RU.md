# Исходный астероид 112: проверенная геометрия и путь к посадке

Дата: **6 ноября 2026 года**. Это офлайн техническая проверка следующего
посадочного backend. Посадка на модель 112 в действующей игре этим изменением
**не включена**. Основной обзор тел и посадок —
[SOURCE_LANDING_INTERACTIONS_AUDIT_RU.md](SOURCE_LANDING_INTERACTIONS_AUDIT_RU.md).

## Практический результат

Настоящий полигональный астероид 112 извлечён из проверенного пользовательского
`FIRSTENC.EXE`. Для него не требуется придумывать сферу или случайный рельеф:

| Свойство | Фактический результат |
|---|---|
| Достижимое замыкание моделей | Только 112, без подмоделей |
| Поток команд | 368 байт, 44 команды, только операции 0/3/4/6 |
| Вершины | 25 парных записей, 50 адресуемых вершин, статический вид 1 |
| Геометрия существующего VM | 60 настоящих треугольников, один экземпляр |
| Независимые исходные вершины | 4 Q31-матрицы × 50 вершин = 200 точек |
| Воспроизводимость native-оракула | 3 свежих процесса, обратный порядок, защитные слова — совпадают |
| Сопоставление VM и проба меша | **224 проверки, 0 ошибок**, включая восемь радиальных пересечений |
| Игровая посадка, исходный collider, добыча | Не реализованы этой проверкой |

Это не только статическое чтение ASM: исходные F1470/F1478 действительно
исполняются в отдельном host-native процессе. Однако исполнение вершин не
подменяет независимый контроль исходных правил столкновения F574/F582/F583.
Триангуляцию и восемь ray/triangle-пересечений выполняет современный адаптер;
они не объявляются исходным алгоритмом посадки.

## Почему нельзя просто разрешить ещё один индекс модели

В действующем `source_world_catalogue.gd` и `source_surface_terrain.gd`
посадочный домен ограничен моделями 117–133. Реальные записи Фобоса, Деймоса
и Амальтеи используют модель **112**. При этом тот же исходный тип 1
«астероидальное тело» может выбирать модель 117: например, Гиперион.
Тип записи и способ получения поверхности — разные признаки.

У 112 есть отдельные исходные особенности:

- Дескриптор по смещению EXE **0x9b5f2** имеет SHA-256
  `c61ebc634cfe7bc3b94f2df7342c5c74b7d0b44740ec62c4dc7ec183b7a2897a`.
  Масштабы `+0x14=12`, `+0x18=0`, внешняя граница `+0x2c=17500`,
  внутренняя `+0x30=0`.
- Указатель физической спецификации **ненулевой**: `0x4b19c2`,
  смещение EXE `0x9b5c2`. Нынешний узкий
  `SourceGroundSurface.initialize_model()` принимает только проверенную
  ветвь без этой спецификации. Её нельзя молча обнулить ради принятия тела.
- Исходный поток столкновения начинается по EXE **0x9b412**, имеет 42 байта
  до массива вершин и начинается `d0 80`. Это группы полупространств,
  обрабатываемые F582/F583, а не поле F581/F1876 с маркером
  `10 82 ff` или `10 83 ff` моделей 117–133.
- Нынешний `SourceGroundSurface.height_raw()` проверяет именно natural-parent
  terrain-домен. Он не является общим вычислителем высоты для любого меша.

Следовательно, расширение диапазона `supported_model()` до 112 либо подмена
радиусом из bounding sphere не доказывают правильную поверхность.

## Откуда брать настоящую поверхность и нормаль

Уже проверенные целочисленные вершины позволяют построить конечный исходный
меш. Радиальный луч из центра пересекает его реальные треугольники. В восьми
проверенных направлениях расстояние до поверхности лежит примерно между
**57 и 279 метрами** по действующей калибровке `16785/2^24 м/raw`.
Это результаты именно этого дескриптора и выбранного source-mesh контекста;
они не объявляются реальными астрономическими размерами Фобоса.

Геометрия асимметрична: проверенные +X и −X дают около 102,45 и 69,66 м,
+Y и −Y — 90,15 и 57,37 м. Одна сфера уничтожила бы эту поверхность.
Нормаль треугольника доступна для современного физического контакта,
но её тождество исходным нормалям/объёмам ещё необходимо проверить.

Исходные нормали и их опорные вершины уже присутствуют в извлечённом ресурсе.
F583 читает их из дескриптора `+0x0c/+0x04`, учитывает знак парного индекса,
масштаб и целочисленное усечение. F582 сочетает проверки в объёмы. Поэтому
следующее независимое доказательство — нативные результаты этих процедур
для точек внутри/снаружи/на границе и разных радиусов корабля, а не только
сравнение raycast с собственным мешем.

Точные исходные участки закреплённого `ffe.asm`:

| Процедура | Начало строки | Назначение в рассматриваемом пути |
|---|---:|---|
| F574 | 36334 | Сброс состояния и публичный запрос столкновения/высоты |
| F575 | 36373 | Broad phase, выбор типа поверхности и контакт |
| F576 | 37052 | Проход collision-программы объекта |
| F579 | 37656 | Подготовка локальной точки, масштабов и вызов F582 |
| F582 | 38524 | Интерпретация collision-групп |
| F583 | 38803 | Проверка одной исходной нормали/полупространства |
| F879 | 64353 | Двухпроходное размещение исходного наземного объекта |
| F1533 | 90970 | Инициализация объекта по дескриптору/спецификации |

Строки относятся к закреплённому JJFFE commit
`7e540341d4e09aa3c92877b87d49e7f2c143ad8d`, а не к произвольной версии.

## Следующая реализация без потери сохранений и взлёта

1. Независимо проверить F1533 для ненулевой физической спецификации 112
   и F582/F583 на настоящих потоках 112. Сохранить исходные байты и охранные
   области, отдельно обозначить границы DOS/JJFFE.
2. Ввести отдельный версионированный backend конечного source-меша.
   Согласовать его видимую геометрию, контакт, нормаль, кадр вращения и
   гравитацию исходного фокусного тела. Обычный планетный квадрат рельефа
   4 км не подходит телу с поперечником в сотни метров без отдельной политики.
3. Подключить этот backend к каталогу, глобальному виду, приближению и
   Surface.enter/restore/takeoff. Старые сохранения 117–133 и v1/v2/v3
   сохраняют прежние контракты.
4. Проверить Фобос, Деймос и Амальтею: подход с разных сторон, опоры,
   ручная и автоматическая посадка, касание ребра, сохранение на поверхности,
   перезапуск и свободный обратный взлёт. Учесть отношение размеров корпуса
   и тела, а не уменьшать корабль ради прохождения проверки.
5. Затем использовать подтверждённый контакт для размещения/подбора MB4.
   Наличие твёрдой поверхности не доказывает наличие пригодного месторождения.

Отдельный исходный класс комет этой проверкой не установлен. Пользовательское
требование о посадке на твёрдые кометные ядра сохраняется как требование
проекта; ему нужны настоящие объекты/геометрия и собственные проверки.

## Воспроизведение и происхождение

Генерация точного ресурса и независимых native-контролей:

```sh
python tools/source_asteroid_surface_spike.py
godot --headless --path . --script res://tools/source_asteroid_mesh_check.gd
```

- [Генератор](../tools/source_asteroid_surface_spike.py) использует сохранённый
  extractor без изменения его логики и точечный constant-only adapter SHA.
  Исходный EXE или существующие игровые JSON не переписываются.
- [Фикстура](../tests/fixtures/source_asteroid_mesh_spike.json):
  SHA-256 `186de87b349b251a4d7658f3abe31fa7a627e58e6865d5166a4a21d4706b9bb1`.
- [Офлайн проверка](../tools/source_asteroid_mesh_check.gd) запускается
  отдельным процессом и подаёт ресурс 112 только его локальному VM.
  Сохранения пользователя не читаются и не записываются.
- JSON результата создаётся в `build/source-asteroid112-mesh-spike.json`.
  Счётчик 224 не добавляется автоматически к прежним отчётам 0.12.0.

SHA-256 EXE:
`d919566140abfc298bc9929bc9141d92526586821f017be1336253a04bca1e72`.
SHA-256 ASM:
`d4f1b76aa78895d3634b182428e14f36ac57b304e56fedb67a89ee39b5f6873a`.

Host-native adapter использует низкие адреса и стек x86-64, сохраняя исходную
32-битную целочисленную арифметику, Q31-входы и реальные потоки вершин.
Проекция отключена; недостижимые projected-only ветви завершают процесс
с ошибкой. Эта проверка не запускает DOS-эмулятор и не подтверждает FPS,
Android, оригинальную collision-программу или готовность всех малых тел.
