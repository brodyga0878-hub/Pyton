# Исходная цепочка линейного движения и адаптер World/Flight

`scripts/source_motion_pipeline.gd` исполняет перенесённую целочисленную
цепочку управления тягой, изменения скорости и координат. В отличие от
номинального SI-образца силы, этот модуль хранит исходное состояние объекта
между шагами: целую скорость, дробные слова скорости и 64-битные координаты.
`scripts/source_motion_bridge.gd` связывает это состояние с настоящими
`World` и `FlightModel` в ограниченном режиме свободного полёта.

Это ядро линейного движения при фиксированном родительском теле. Полный
исходный диспетчер полёта игрока, вращения корабля и смены системы отсчёта
здесь не заявляется. Подключение адаптера к основному игровому циклу и
версионирование общего сохранения выполняются отдельно; наличие этих
модулей само по себе не означает завершённую интеграцию Main.

## Перенесённые процедуры

| Исходная процедура | Runtime API | Содержание |
| --- | --- | --- |
| F598 | `set_thrust(body, command, "maximum")` | Исходное формирование максимальной команды: знак X/Y, сдвиг Z и ограничения осей. |
| F599 | `set_thrust(body, command, "limited")` | Ограничение команды шестью знаковыми словами тяги объекта. |
| F600 | `set_thrust(body, command, "direction")` | Исходный расчёт коэффициента и масштабирование вектора команды. |
| F607 | `desired_acceleration(body, set_speed)` | Расчёт остатка до заданной скорости и команды в локальных осях корабля. |
| F601 | `velocity_step(body, ticks, true)` | Изменение скорости с исходными дробными остатками и ограничением по остатку заданной скорости. |
| F602 | `velocity_step(body, ticks, false)` | Другой исходный вход изменения скорости, без ограничения F601. |
| F603 → управление → F601/F602 → F1512 | `manual_step(...)`, `advance(...)` | Гравитация родителя, управление тягой, изменение скорости, затем перенос координат. |

F603 и F1512 вызываются через `source_gravity.gd`. Гравитационный параметр
берётся из исходной записи тела через `Gravity.coefficient(record)`; в эту
цепочку не добавляются выдуманные GM или отдельная модель N-body.

Сохраняются особенности исходной арифметики, включая переполнения s32,
порядок операций и знаковые сдвиги. В частности:

- F601 начинает с логического `SHR ticks, 3`; начальный показатель для
  большой ветки равен **16**.
- F602 начинает с арифметического `SAR ticks, 3`; начальный показатель
  большой ветки равен **15**. Эти входы нельзя свести к одной формуле,
  отличающейся только последующим ограничением скорости.
- В F600 очередная ограниченная ось перезаписывает коэффициент в исходном
  порядке X/Y/Z. Это не выбор минимума всех коэффициентов.
- F607 сохраняет исходную поправку заданной скорости на `speed / 100`
  с целочисленным усечением и последующие операции F1515/F1516.
- Наличие дробной части скорости не означает непрерывную SI-интеграцию:
  F1512 сохраняет собственное исходное квантование переноса координат.

В композиции при `engines_off = false` порядок равен
`F603 → F607 → F599 → F601 → F1512`. При `engines_off = true` он равен
`F603 → F599(command) → F602 → F1512`. Имя параметра обозначает выбор
исходной ветки; ненулевая явная команда в последнем режиме всё ещё даёт
тягу. Нулевая команда используется для свободного хода.

## Исходное состояние и единицы

Объект и его фиксированный родитель представлены отдельными массивами по
**338 байт**. Существенные поля объекта:

| Смещение | Представление |
| --- | --- |
| `0x00…0x23` | Девять s32-компонентов ориентации Q31, три группы локальных осей. |
| `0x3e`, `0x46`, `0x4e` | Три знаковые 64-битные координаты относительно родителя. |
| `0x8c…0x97` | Три целые s32-компоненты скорости. |
| `0xb6…0xbb` | Три текущие s16-команды тяги. |
| `0xbc…0xc7` | Шесть s16-ограничений тяги. |
| `0xec`, `0xee`, `0xf0` | Три беззнаковых 16-битных дробных остатка скорости. |
| `0xf2…0xfd` | Три s32-остатка до требуемой скорости. |

Преобразование на границе SI:

```text
position_m = position_raw_s64 × 16785 / 2^24
velocity_m_s = (velocity_s32 + fraction_u16 / 65536) × 16785 / 172800
nominal_ticks_per_second = 2^32 / 86400 ≈ 49710.2696296
```

Отрицательная скорость также использует целую часть плюс положительную
дробь: при кодировании адаптер берёт `floor(raw_velocity)`, затем остаток.
Это существенно для корректного продолжения движения после сохранения.
`decode_si(body)` возвращает числовые массивы, сохраняя явную пометку
`unaltered_source_world_axes`.

Адаптер использует Cobra из исходной спецификации: модель **38**, масса
**100 тонн**, исходное поле массы `0xe4 = 400`. Ограничения тяги в порядке
`left, right, up, down, forward, retro`:

```text
3815, -3815, 3815, -3815, 10900, -3815
```

Никакой дополнительный множитель мощности двигателя к этим словам не
применяется. Другие корабли этим адаптером пока не поддерживаются.

## Оси, начало координат и управление телефона

Глобальные X/Y/Z исходного мира переходят в Godot без отражения и
перестановки. Для ориентации применяется отдельная явная политика
`identity-world-axes-proper-local-yaw-pi-q31-v1`:

```text
B = Basis(ship.attitude.normalized())
R = Basis(-B.x, B.y, -B.z) = B × Ry(π)
```

Это локальный поворот на π с положительным определителем. Исходные `+X`
влево, `+Y` вверх и `+Z` вперёд согласуются с авторским кораблём, у которого
направление вперёд равно `-Basis.z`. Отражение одной глобальной оси не
используется. Компоненты R кодируются в Q31 округлением масштаба
`2147483647`; ориентация обновляется из текущего управления телефона.
Этот адаптер ориентации не исполняет исходную угловую динамику F585.

Исходная позиция вычисляется относительно физического родителя:

```text
p_relative_parent = ship.position - world.local_meters(focus_id, days)
```

Вычитание выполняется по компонентам в double precision. Для вывода
используется локальный якорь и **разность исходных целочисленных
координат**: это позволяет сохранить малое локальное перемещение рядом с
родительским телом, расположенным в десятках миллионов метров от arrival
origin. Сырые координаты и дроби остаются авторитетными; повторное
кодирование всех скоростей из `Vector3` на каждом тике не выполняется.

В режиме `ship.assisted` адаптер передаёт заданную скорость в F607/F601.
Без `assisted` положение телефонного рычага
`clamp(target_speed / MAX_SPEED, -1, 1)` задаёт долю реального исходного
forward/retro-предела и использует F599/F602. Это явно обозначенный
аналоговый адаптер телефона, а не перенос исходного обработчика клавиш.

## Контракт адаптера и отказ от неподдерживаемого шага

Основной API:

```gdscript
Bridge.eligible(world, ship, surface_active := false)
bridge.configure(world, ship, elapsed_days)
bridge.step(dt_seconds, ship, world, elapsed_days, lift := 0.0)
bridge.is_active()
bridge.elapsed_days()
bridge.synchronized(world, ship, elapsed_days)
bridge.reset()
bridge.snapshot()
bridge.restore(saved, world, ship, elapsed_days)
```

`step` возвращает словарь с `ok`, `handled` и `reason`. Только результат
`handled = true` означает, что адаптер уже изменил `ship.position` и
`ship.velocity`: вызывающий код не должен повторно применять перенос
координат или ещё один гравитационный импульс к тому же шагу.

Текущая область допуска: исходный полный мир
`source_jjffe_systems_v4`, живая Cobra, естественный родитель с проверяемой
68-байтной исходной записью, фиксированный arrival frame. Исключены звезда
и barycenter в качестве focus, выбранный site/порт, доступная станция,
стыковка, поверхность, бой, автопилот и незавершённый transfer.
Внешний `surface_active` также исключает допуск. Вызывающий код должен
учитывать этот внешний флаг; сам `step` проверяет состояние корабля.

Допустим один шаг `0 < dt ≤ 0.1` секунды. Он переводится в номинальные
тики с переносом остатка `[0, 1)` на следующий шаг. Это политика
`nominal-day-si-tick-fraction-v1`, **не** выполнение исходного таймера
F1418 и не заявление о полном оригинальном планировщике ускорения времени.

Ненулевая вертикальная помощь `lift`, выход из допустимого контекста или
внешнее изменение положения/скорости сбрасывают raw state и возвращают
`handled = false`. Существующий путь полёта должен обработать такой шаг.
Следующий допустимый шаг может заново привязать raw state к актуальному
состоянию корабля. При проверке контекста контролируются system/focus,
SHA записи родителя, постоянство его локального центра и согласие с
выведенными положением и скоростью. Ошибка вычисления откатывает состояние
шага; некорректные время и входные значения отклоняются до интеграции.

Перед сохранением или сменой начала координат вызывающий код может
проверить `synchronized`: кроме текущих положения, скорости и родителя,
этот метод сверяет дату и ориентацию Q31. Так старый raw state нельзя
случайно сохранить сразу после прыжка, внешнего изменения ориентации или
коррекции положения. Это проверка завершённого состояния между шагами;
перед обычным `step` время и ручная ориентация уже могут быть продвинуты.

Ограничение на станционные кадры принципиально: при начале координат,
следующем станции, локальная скорость корабля не равна скорости
относительно планеты. Требуется проверенное преобразование скорости
`v_origin − v_parent`. Текущий адаптер не подменяет его совпадением
координат и не выполняет автоматический выбор или смену родителя.

## Сохранение и продолжение

Ядро сохраняет профиль `source-fixed-frame-linear-motion-v1`, схему
`starfrontier-source-motion-state-v1`, версию 1 и полные `body_hex` /
`parent_hex`. Hex сохраняет все исходные байты без потерь JSON.

Адаптер имеет отдельную схему `starfrontier-source-motion-bridge-v1` и
контракт `source-fixed-natural-parent-phone-motion-v1`. Помимо raw state,
он сохраняет system/parent, SHA исходной записи родителя и спецификации
Cobra, политики осей и часов, локальный якорь и его raw hex. Остаток тиков
и дата записываются как точные 8-байтные IEEE-754 значения:
`ticks_fraction_f64_hex`, `elapsed_days_f64_hex`.

У активного адаптера `elapsed_days()` возвращает точную номинальную дату;
у неактивного возвращается `NaN`. После успешного строгого восстановления
Main использует эту дату для кандидата Navigation: обычная десятичная
сериализация JSON иначе меняла её младшие биты. Отдельный фактический
Main-контроль трёх последовательных сохранений, включая повёрнутый корабль,
проверяет **28 условий, 0 ошибок**: следующий raw body, остатки, координаты,
скорость, quaternion и навигационные часы совпадают точно.

Restore требует точного набора полей, подходящих версии и контракта,
конечных чисел, согласованной даты, правильных hex-длин и текущего
World/Flight-контекста. Он проверяет исходные постоянные поля объекта,
массу, родителя, ориентацию и якорь. Валидация проходит на отдельном
кандидате; ошибочное сохранение не заменяет живое состояние.
Верхний уровень должен включать этот профиль явно и сохранять старую
политику для прежних версий сохранений; сам адаптер не мигрирует их.

## Независимый нативный контроль

`tools/rebuild_source_motion_native.py` извлекает закреплённые исходные
инструкции из `jjffe/ffe.asm`, собирает отдельный host ELF и получает
ожидаемые байты непосредственно от них. Ожидания не вычисляются
GDScript-реализацией. Здесь host ELF служит инструментом разработки;
x86-код не требуется Android-игре во время выполнения.

Нативный набор содержит **1236 случаев**: восемь режимов процедур и
композиции, крайние целые значения, знаки, ограничения, разные ориентации,
малые/большие шаги и последовательные зависимые шаги. Три запуска в новых
процессах дают одинаковые результаты; повтор в обратном порядке исключает
зависимость от порядка. Проверяются защитные байты вокруг объектов и
банка, неизменность родительского банка. Для host ABI явно выполнены
адаптация стека/регистров, исходного `abs`, низкоадресных объектов и
резерва scratch-памяти F1670 с 8 до 16 байт под два host pop; арифметика
исходных процедур и её смещения сохранены.

`tests/test_source_motion_pipeline.gd`: **5240 проверок, 0 ошибок**.
Сравниваются все 338 байт результата с независимым fixture, а также
сохранение/продолжение, зависимые шаги и атомарное отклонение ошибок.
`tests/test_source_motion_bridge.gd`: **81 проверка, 0 ошибок** на
настоящих World/Flight. Проверяются реальная Cobra, оси, родительская
позиция, малые скорости с дробями, якорный вывод, остатки часов,
тождественное продолжение после JSON restore и исключённые контексты.
Это контроль указанного ядра и границы SI, а не Android-бенчмарк или
доказательство полноты всей физики оригинала.

## Самостоятельные преобразования F572/F573

`scripts/source_frame_kinematics.gd` переносит полные исходные процедуры
поворота объекта F572/F573. Профиль:
`source-f572-f573-rotation-primitive-v1`. API:

```gdscript
Frame.rotate(body338, matrix9Q31, enter_rotating, source_frame_byte := 1)
```

Вход содержит 338 байт объекта и девять s32-компонентов матрицы Q31.
`enter_rotating` требует настоящего boolean: `true` выбирает F572,
`false` — F573. `source_frame_byte` — целое от 0 до 255. Возвращается
словарь с новым `body`, процедурой, профилем и `truncate_shift`; ошибочные
входы дают пустой словарь. Входные объект и матрица не изменяются.

Преобразуются координаты, три группы ориентации и **целые** компоненты
скорости. Сохраняется исходная потеря точности:

- 64-битная позиция проходит `Vec64Truncate28`; после поворота исходный
  масштаб восстанавливается, но отброшенные младшие биты не возвращаются.
- Каждый член произведения Q31 усекается отдельно, затем выполняется
  исходное суммирование s32. Одна итоговая операция с плавающей точкой
  не даёт эквивалентный результат.
- При входе `body[0x57] = 1`, а `body[0x58]` получает
  `(source_frame_byte - 1) & 255`. При выходе `body[0x57] = 0`, а `0x58`
  сохраняется.
- Три дробных слова скорости Q16 по `0xec…0xf1` остаются **неизменными**,
  как в самих исходных F572/F573. Они не поворачиваются вместе с целой
  скоростью.

Поэтому композиция «вход → выход» или «выход → вход» не обязана возвращать
начальные байты. Контроль использует реальные составные нативные
результаты с потерями, а не искусственное требование обратимости.

Независимый инструмент `tools/rebuild_source_frame_native.py` получает
ожидания от полных исходных инструкций. Набор
`tests/fixtures/source_frame_native.json` содержит **720 случаев**:
F572, F573 и обе последовательные композиции, крайние координаты,
различные матрицы и байты кадра. Подтверждены три одинаковых запуска в
новых процессах, обратный порядок случаев, защитные байты и неизменность
матрицы. `tests/test_source_frame_kinematics.gd` выполнил
**3625 проверок, 0 ошибок**, включая полное побайтовое сравнение объекта,
сохранение дробей скорости и некорректные входы.

```sh
python3 tools/rebuild_source_frame_native.py --source /workspace/ffe-upstream/jjffe/ffe.asm
godot --headless --audio-driver Dummy --path . --script tests/test_source_frame_kinematics.gd
```

Это готовые самостоятельные арифметические примитивы. Сами процедуры
не выполняют перенос начала координат между родительскими телами и не
прибавляют/вычитают `ω × r`. Полный вызывающий контур F570/F606 и
автоматический выбор системы отсчёта ещё не перенесены. Подключать
F572/F573 как готовую автоматическую смену кадра нельзя; живой SI-адаптер
по-прежнему ограничен фиксированным естественным родителем.

## Что ещё требуется для полной исходной динамики

Здесь не реализован полный вызывающий контур F585/F606, исходная угловая
динамика, автоматическая смена системы отсчёта, атмосфера, топливо,
столкновения и глобальная событийная цепочка игрока. Перенесённые
F572/F573 дают только описанный выше исходный поворот полей объекта;
для полноценного перехода между системами отсчёта остаётся работа с их
вызывающим контуром. Адаптер намеренно возвращает управление прежнему
пути в неподдерживаемых контекстах. Сохранённая исходная арифметика
линейного шага не должна описываться как полностью клонированная механика
полёта FFE.
